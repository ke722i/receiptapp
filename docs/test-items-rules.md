# 11. テスト項目書（TEST_ITEMS.md）

## Excel に変換するとき（TEST_ITEMS.md → TEST_ITEMS.xlsx）
プロジェクトの直下で、次を実行する。

```
python tools/export_test_items.py TEST_ITEMS.md TEST_ITEMS.xlsx
```

- **何ができるか**: テスターが結果（OK／NG／対象外）を書き込める Excel ができる。シートは、使い方／**集計**／機能一覧／単体テスト／結合テスト／見た目の確認／不具合一覧（空）／既知の未対応／変更履歴／付録(開発者向け)。
- **集計シート**: 全体・テストの種類ごと・区分ごとの、項目数／OK／NG／対象外／未実施／**合格率**／実施率が、自動で計算される。
  **合格率 ＝ OK ÷（項目数 − 対象外）**。対象外は分母から除き、未実施は合格に数えない。完成の目安は、全体の合格率が 100%。
- **準備**: Python と openpyxl が必要。Python が PATH に無い PC では、Python をフルパスで呼ぶ。
- **元は `TEST_ITEMS.md`**。Excel は、そこから作る成果物。Excel を直接直さず、項目を直すときは、md を直して、作り直す。
- **Excel（`TEST_ITEMS.xlsx`）は、リポジトリ（Git）に入れない**（`.gitignore` に指定済み）。結果を書き込む、手元のファイルで、このスクリプトで、いつでも作れるため。
  コミットのときも、含めない。Excel を開いている間にできる `~$TEST_ITEMS.xlsx`（Excel のロックファイル）も、`.gitignore` で無視している。
  Excel を開いたままだと、作り直し（上書き）はできないので、閉じてもらってから行う。

**注意（必ず守る）**
1. **Excel（TEST_ITEMS.xlsx）は、頼まれたとき（テストを依頼する前など）だけ作る。** md を直すたびには作らない（使用量を抑えるため。ユーザーの指示）。作るときは、確認なしで上書きしてよい（結果の記入は、完成後の最後のテスト期間だけ）。
   ただし、**作り直すと、Excel に書き込まれた結果は消える。** 最後のテストで結果を書き込み始めたあとは、上書きせず、別の名前で出力して、差分だけを反映する（そのときは、ユーザーに確認する）。
3. md の表の形（列の名前・「前提:」の行・「### 8-」の見出し・`- [ ] DV-` の形）を変えるときは、スクリプトも合わせて直し、出力した件数が、md の件数と一致することを確かめる。
4. 集計の数式を変えたときは、例（50件・50 OK → 100%、25 OK・25 NG → 50%、45 OK・5 対象外 → 100%）で、数式が合うか確かめる。

## 項目書の書き方
アプリの完成後に、**別のメンバーが手動で**、単体テストと結合テストを行うための項目書。自動テスト（`npm test`）は、作らない。
見つかった不具合は、ユーザーがまとめて私に送る。私が、デバッグ・修正し、直ったら、再テストする項目を知らせる。完成は、すべての項目が OK になったとき。
- **更新するとき**: 「引き継ぎして」と頼まれたときに、それまでの変更をまとめて書く（機能を作るたびには更新しない。使用量を抑えるため）。
- **読む人は、コードを読めないメンバー**。本文（1〜7章）は、画面の操作だけで、できるように書く（関数名・ファイル名は書かない）。
- **構成**（章の番号と見出しは、今の TEST_ITEMS.md に合わせる）
  1. 「テストを行う方へ」: 流れ、環境、アカウントとデータ、結果の付け方、**不具合の報告のしかた**（テンプレート）。
  2. 「機能の一覧と状態」の表: 機能ごとの状態（✅ 公開済み／🔧 作成中・未コミット／⚠ 一部未対応）と、これまでの確認の状況。
  3. **単体テスト**（手動）: 機能・画面ごとの表。ID は `UT-区分-番号`（区分は A〜L、T、F2 など）。列は「ID／操作／期待結果／結果／メモ」。
  4. **結合テスト**（手動）: 複数の画面・機能をまたぐ流れ。ID は `IT-番号`。列は「ID／前提／手順／期待結果／結果／メモ」。
  5. **見た目・操作感の確認**: ID は `MT-番号`。
  6. 「既知の未対応・注意」: テスト対象外にするもの（今の仕様の穴）。
  7. 「変更履歴と、その変更で確認すること」: 新しい順。変更の内容と、確認する項目の ID を結びつける。
  8. **付録: 開発者向けの内部仕様**（ID は `DV-モジュール-番号`）: 関数・DB の関数・部品ごとの、入力と期待結果。**デバッグの参考**で、メンバーは読まなくてよい。
- **項目の書き方（本文）**: 「操作」は、1つの操作で、期待結果が1つに決まる形にする。「期待結果」は、画面に見えること（表示される文言、並び順、数、色）を、具体的に書く。推測で書かず、コードや動かした結果から書く。
  特別なデータ・別のアカウント・管理者の作業が必要なときは、「前提」に書く。ID は、既存の番号の続きに振る。新しい機能は、新しい区分と表を足す。
- **作成途中の機能**も書く。状態は 🔧 にして、項目の操作の末尾に 🔧 を付ける。マージされたら、✅ にして、🔧 を外す。
- **「結果」の欄は、空欄のまま**にする（実施するメンバーが書く）。ユーザーが「確認できた」と言ったことは、「機能の一覧と状態」の表の「これまでの確認の状況」に、その範囲（機能全体か、項目ごとか）を分けて書く。確認していないことを、確認済みとして書かない。
- **付録の「○」**: 私が、一時的な作業フォルダのテストで、期待どおりになることを確かめた項目。メンバーの手動テストの代わりではない。確かめていない項目は、空欄にする（実際に動かしていないことを、○にしない）。
- **不具合の報告を受けたとき**: 報告の項目 ID から、本文の期待結果と、付録の内部仕様（DV-）を見て、再現し、原因を調べて直す。直したら、変更履歴・状態を更新し、再テストする項目の ID を知らせる。
  報告に、パスワード・API キー・他人の個人情報が含まれていたら、使わずに、書き直してもらう。
- 最終更新の日付を、更新のたびに直す。
